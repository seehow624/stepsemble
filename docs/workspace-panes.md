# Managed workspace and session panes

Implementation branch: `codex/workspace-panes`. This changes source only; the installed Host is not restarted or upgraded.

## Product behavior

- `/` opens the workspace shell. The sidebar reads only the Host's explicit workspace registry. Adding a folder records the project without importing history or launching an agent.
- New Stepsemble conversations join automatically. Older conversations stay under **History from other apps** until explicitly added. Viewing and adding history do not launch, stop, or take control of an external process. Resume remains dependent on the connector's existing capabilities.
- With more than one computer, every computer's sessions share one list: **Recent**, the five most recently used sessions on any computer (those at work first, each naming its computer), then the Bots, then each computer with its projects, the current one first. A session from another computer opens on that computer, and its project's **+** starts a new session there. The current computer, which Settings, Schedules and the allowances follow, keeps ordering and pins; **Use this computer** in another computer's menu makes it the current one. The other computers' lists are read every ten seconds; one that stops answering is marked offline with the time it was last seen and keeps its last list, dimmed. Folded computers are remembered in the browser. With one computer the list is as before.
- A project with more than three sessions lists its first three and a small **Show N more** line; one click shows them all, and **Show fewer** folds them again for as long as the page is open. A session open in a pane stays listed while folded, a folded session that is working or has an unread result puts a dot on the line, and a search lists every match.
- A pane shows one session; there are no tabs. The top-left pane is the main one: clicking a session in the sidebar shows it there, replacing the main pane's session, and the other panes keep theirs. An empty pane in focus, such as one a split just made, takes it instead, and a session already shown in a pane takes the focus without moving. New sessions, Schedules and notifications open the same way; **Branch in new chat** opens beside the conversation it came from.
- Each pane has a title bar with its session's agent, name and, with more than one computer, the computer. Drag the name to move the session: onto another pane's middle or title bar to take its place, or to one of its four edges to split. A session moved away leaves no empty pane behind. The title bar's **Summary** opens the conversation's goals, subagents, the files it wrote and what it read; its **⋯** menu holds Rename, Pin, View changes, the splits, Move to new window, Maximize, the conversation's own **More…** sheet and Close pane. Closing a pane's session (its **×**, a middle click on its name, or Cmd+W) closes the pane too while others remain; the last pane stays, empty. A layout saved while panes held tabs keeps each pane's shown session.
- **Cmd+Option+Left/Right** moves the focus to the previous or next pane, including from a conversation input. Background name/status polling preserves the mounted conversation, including drafts and scroll. The divider supports pointer dragging and arrow keys.
- Up to eight panes per window. **Move to new window** in a pane moves its session to a separate browser window, once the destination has saved and acknowledged its layout. Popup blocking keeps the source intact. Existing windows can accept dragged sessions through the same-origin transfer channel.
- On macOS, owned title-bar mouse tracking distinguishes a real release from Escape/cancellation. A release onto another visible workspace uses its pane/split targets; a release outside all visible Stepsemble windows, within a display's usable area, opens a separate window through the same persisted/acknowledged transfer. This is a tear-out, not a data drop into another app. Loss of activation, navigation, timeout and cancelled tracking retain the source. Only the app's own windows are hit-tested; no desktop identity, screen pixels or screen-recording permission is required. Arbitrary HTML `dragend`/`dropEffect=none` never opens a window. In browsers, the pane's **Move to new window** menu remains the safe tear-out alternative; blocked popups retain the source.
- In a conversation, scrolling back to near the top loads the next earlier page by itself, keeping the reading position, as chat apps do. Only the person's own scrolling (wheel, touch, keys, scroll bar) triggers it, one page per approach. **Load earlier messages** stays at the top for keyboards, screen readers and a retry; a failed page is not retried by scrolling.
- Closing a pane or window detaches its viewer. It does not issue a stop/close command to the Host. Stop remains an explicit action inside the conversation.
- Layouts persist per browser window identity, independently of the Host's session registry. A simultaneous second copy of a window URL receives a new identity when Web Locks are supported. On mobile, one focused pane is shown with **Next pane** for navigation.
- Codex/Claude subscription windows appear in the footer when available. Missing data is `—`, never zero. The detail dialog includes reset times and last confirmation.
- When the Host cannot be reached (a computer waking up, Wi-Fi or a VPN reconnecting, Stepsemble restarting after an update), the Workspace stays on screen and reconnects by itself. Offline, the service worker answers a Workspace URL with the cached Workspace, never with the single-conversation page. A pane that cannot reach its Host says so and opens its conversation once the Host answers; a sign-in started from the Workspace returns to it even if the device list is briefly unavailable.
- On a phone, swiping from a conversation's left edge returns to the Workspace list like the pane's back button; the pane keeps its conversation.
- In the Mac App, **Cmd+W** closes the focused pane's session. Closing the last one keeps the empty workspace window open. **Cmd+Shift+W** closes the window. Closing a viewer never stops the session's work.
- Within a project, sessions are listed by their latest activity: pinned sessions first, then a session at work, then the one with the most recent turn or reply, down to the one unused longest. The Host records a session's latest turn start or end; a session not used in Stepsemble yet takes the time of its own history file. A session that moves up while the pointer is over the list, or while a menu is open, waits until the pointer leaves, so a row never jumps under a click; a redraw keeps keyboard focus on the same control. Sessions are not reordered by hand; dragging one only places it in a pane.
- Projects have **Pin to top**, **Move up** and **Move down** in their action menus, and sessions have **Pin to top**. Drag a project with a mouse or a finger to arrange projects; Alt+arrow keys on a focused project do the same. Pinned items stay above unpinned items. Project order and pins are saved on the selected Host and shared by its devices. A cancelled drag or a drop outside the list keeps the previous order.
- Settings opens on the workspace's current Host; changing the Host in Settings also changes the workspace sidebar. An unavailable requested Host never falls back to editing the local Host. About and Updates share fixed navigation and title positions, with independent content scrolling on desktop.
- Goals and Schedules share a stable **New** header action. The selected mode determines what it creates.
- Notifications cover completions, failures, stops and approval requests for managed work. The Mac App uses macOS notifications; browsers use Web Push with a separate subscription for each Host. Enable them under Settings → Notifications on each device/Host, and use **Send test notification** to check permission and delivery: it reports the push service's answer, so a refused notification is not shown as sent, and a refusal is also written to the Host log. On an iPhone or iPad, Web Push needs Stepsemble added to the Home Screen and opened from there. Viewing the matching session suppresses the alert (a browser that requires every push to show something, such as Safari, gets a notice that closes at once); clicking an alert opens that session on its original Host. Goal continuation turns stay quiet, with approval requests and final outcomes still reported. Notifications include the session title, never transcript or prompt text. A newer alert for a session replaces its older one and still alerts; an approval request or a Goal that needs attention stays on a desktop until it is answered, and each alert shows when the event happened. Alerts use the device's language; changing the language updates that device's subscription on the selected Host. When the browser blocks notifications, Settings says where to allow them (the site settings, or Settings › Notifications › Stepsemble on an iPhone or iPad) and checks again when the person comes back.

## State and runtime boundaries

`~/.config/stepsemble/workspaces.json` stores versioned project paths and stable membership UUIDs with a small allowlist of native identity metadata. It contains no transcripts or credentials. Atomic replacement protects writes; a corrupt file fails closed instead of being overwritten. Removing membership preserves native session files.

Its optional `presentation` stores project/session order and pins, separately from native identities. Unknown or removed memberships are discarded from that metadata. Notification cursors contain only bounded recent lifecycle facts in memory; a fresh subscription or a Host restart never replays old completions.

The shell owns a binary split tree and placement only. Same-origin conversation frames reuse the established agent renderer and authenticated Host APIs, with frame-specific host/session identities. Loaded frames remain mounted during splits, moves and resizing; a session replaced in a pane lets its viewer go. The embedded renderer skips global history inventories and never restores an unrelated last-opened conversation.

Pi learns its persistent file identity after launch. Claude records its native identity when observed and retains the same membership after resume; simultaneous resume requests are serialized to avoid duplicate processes. This does not add a daemon or alter the existing Host's process lifetime guarantees.

Cross-window moves use `BroadcastChannel`, a one-use pending transfer token, and destination persistence before acknowledgment. The source remains when destination startup or storage fails. A destination reload reattaches through existing provider APIs; it does not clone a native session. Browsers without BroadcastChannel cannot acknowledge a cross-window move and retain the source view.

Only `/index.html?pane=1` permits same-origin framing. Ordinary pages retain `X-Frame-Options: DENY`; API authentication, origin checks, and browse-root restrictions remain in force.

Quota reads use Codex's native `account/rateLimits/read` through its history connection without allocating a thread. When that connection cannot answer, for example because the installed Codex CLI speaks an app-server schema this release has not reviewed, the same allowance is read from ChatGPT's usage endpoint: first with the account the Codex CLI is signed in to, then with the ChatGPT account signed in under Settings. Claude uses its existing OAuth credential on the Host (credential file, or macOS Keychain when applicable), then the Claude account signed in under Settings, against Anthropic's usage endpoint. OpenCode Go and MiniMax API keys saved under Settings are probed on their own platform's host; a MiniMax China key goes to the China host. The Codex CLI's token is only read and never renewed, and an expired token is never sent. A Settings sign-in close to expiry is renewed through Pi's own locked refresh, as a Pi run would renew it. Saved keys that run a command or refer to an environment variable are left to Pi. Credentials stay on the Host and are never returned to the browser or registry. `STEPSEMBLE_WORKSPACE_KEYCHAIN_USAGE=0` disables Keychain reads. Provider errors are isolated; requests coalesce and cache for five minutes on success or one minute on failure. The ChatGPT fallback through both sign-ins and a saved MiniMax key were read live on a signed-in Host; the Claude Settings sign-in path is covered by tests only.

## Validation and preview

Run `npm run preview:workspace` for an isolated loopback Host with disposable synthetic sessions and no provider credentials or executable agents. The script prints its URL and a synthetic local-only login token; Ctrl-C stops its child and removes its temporary fixture. Build/test copies and generated data belong on a local disk, not SMB.

For isolated native tab QA, run `scripts/workspace-tabs-preview.mjs` from a local source copy, then `node scripts/workspace-tabs-native-harness.mjs /tmp/owned-output http://127.0.0.1:PORT native-composer-preview`. The harness compiles the actual window/drag implementation with a distinct bundle id, nonpersistent WebKit storage and only the synthetic fixture; it does not discover the installed Host or activate itself. Test click/threshold, reorder, cross-pane/window drop, release outside the app, Escape, iframe keyboard shortcuts and popup Cmd+W with normal user activation. Compilation and browser automation alone do not establish native drag runtime correctness.

Automated tests cover registry persistence, corrupt-state handling, stable native identity, split/layout bounds and host isolation, authenticated HTTP membership/history operations, unchanged task records, iframe headers, quota normalization/caching, Codex quota transport/pool routing, and concurrent Claude resume. Existing browser suites deliberately visit `/index.html` to continue testing the original conversation controller. Local UI verification uses Codex Computer Use; browser automation suites remain CI-only.

Manual synthetic verification: sidebar-to-right-edge drag; two independent session panes; layout reload; mobile single-pane layout; opening an independent window and removing the source only after acknowledgment; external history remaining outside membership. No real model prompts, installed-service restart, or production deployment were used.

## Release candidate validation (2026-09-21)

Source version: `3.1.0-rc.1`. No installed Host has been upgraded and no public release has been published. Existing active tasks remain untouched.

The workspace uses explicit translation keys in all eleven supported locales. Native names, paths, and output bypass translation. Saved language, light/dark/system appearance and text size apply to the shell; cross-window settings events update already loaded conversation viewers without replacing their frames. Design palette selection remains owned by the established conversation renderer.

Release checks: syntax, client generation, protocol generation, native composer syntax, shell syntax and 1,251 independent protocol conformance cases passed. The final Node test run covers 1,545 tests (1,541 pass, four existing skips). Browser verification uses isolated synthetic fixtures, including settings changes with two panes and restored layout. Live-account quota and live-provider multi-window smoke remain unverified; no model call was made for this candidate.
