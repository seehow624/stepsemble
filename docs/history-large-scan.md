## 問題與本段界線

目前 Codex 路徑先將整個 rollout 放入 Rust capture、Node frame 及 parser snapshot，
畫面分頁不能解決這些整檔配置。直接將 8 MiB 改成更大數字，會增加 Host 記憶體與
複製負擔，也不解決完整紀錄驗證。本段先提供可重用的逐段掃描核心，後續才接來源
權限、固定版本格式與全鏈；沒有放大舊協定或 permissioned worker 的 heap/grants。

`jsonl_scan::scan_matching_page` 只接受 caller-held `Read + Seek`，不開路徑、不呼叫
native CLI、不修復資料、不產生 session/turn/approval。它是 byte-level primitive：
**不自行宣稱 JSON/UTF-8、thread ID、native version、history mode 或名稱已驗證**。
caller 的逐筆 validator 必須驗完整來源；所有內容仍是不可信資料。
官方 [App Server 文件](https://learn.chatgpt.com/docs/app-server) 將 stored read 與 resume
區分，並說明實驗分頁能力依 active store 而定；本段沒有以它替換固定 0.153.4 的
格式／來源證據，也沒有啟動 resume、模型或新原生方法。

## 核心契約

- 最多 256 MiB／262,144 筆；每次 read request ≤64 KiB、單筆含 LF ≤128 KiB。
  這些是**新內部核心的硬上限，不是已公開的產品能力**。
- 每頁 ≤50 筆且原始 bytes ≤256 KiB；只保留一頁、一個 record buffer 和 read chunk，
  不建全檔 bytes 或所有行 offset 陣列。原始 LF/CRLF、空行、未知與 binary bytes 不改寫。
- `offset` 是來源 record ordinal；byte budget 只能在完整 record 間停止，`next_offset`
  不能跳過未回傳的紀錄。offset=EOF 可回空頁，大於 EOF 拒絕。
- 第一輪掃描整檔、逐筆呼叫 borrowed validator，頁滿後仍繼續；任何後段格式／tail／
  單筆／筆數錯誤均不回頁。validator 不是發布 callback，不能留存無界狀態。
- 在同一 reader rewind 後第二輪再掃整檔，對比長度、筆數、SHA-256；可要求與上一
  page 的 expected summary 相同。第二轮不重複有狀態的語義 callback、不保留第二頁。
  檢查未選中頁內容的變動，不僅比較選中頁；不是原子 snapshot 或逐 byte literal equality。
- observed length 之外最多試讀一 byte，增長／縮短拒絕；不丟棄未完成 tail 而報成功。
  每個 read／record／rewind／EOF/return 邊界接受 caller checkpoint，EINTR 重試亦受限。
  checkpoint 的 cancel/budget 不會被「已有第一頁」跳過。seek error/錯位均拒絕。
  checkpoint 是合作式檢查，不能中斷卡住的底層Read/Seek；接線仍須獨立程序的硬逾時、
  強制終止和actual close確認，不能以此callback取代既有Host收尾機制。
- 所有錯誤只回 enum，不夾帶路徑／內容／OS 訊息。失敗後沒有 Page；沒有授權、
  publishable 或 cleanup receipt。記憶體釋放不等於安全抹除，不聲稱 wiped/zeroized。
- 原始 256 KiB **不是 JSON wire budget**：escape、header、metadata/structure 還須分別
  有界；不能把本段 Page 直接序列化到舊 272 KiB wire 或稱為 validated capture。

### 直接配置量量測

`examples/owned_jsonl_scan.rs` 在獨立 executable 用 System allocator 計數。generator
只持有一筆記錄，逐筆進行真的 serde JSON parsing；不先配置整個大檔。全頁 bytes、
full digest／count、兩輪總讀取量與釋放回 baseline 都有斷言。該 allocator **只在 example**，
沒有裝到 Host／source reader，也沒有新依賴或 Cargo.lock 修改。

同一最佳化版連續三輪：

| 來源／單筆 | 第一輪峰值 live allocation 增量 | 三輪耗時範圍 |
| --- | ---: | ---: |
| 1 MiB／1 KiB | 253,050 bytes | 5.08–5.56 ms |
| 32 MiB／1 KiB | 253,050 bytes | 155.95–175.54 ms |
| 256 MiB／1 KiB（262,144筆） | 253,050 bytes | 1,291.33–1,333.23 ms |
| 1 MiB／128 KiB | 594,042 bytes | 5.23–5.55 ms |
| 256 MiB／128 KiB | 594,042 bytes | 1,246.12–1,252.90 ms |

三輪同 workload 的配置量完全相同；selected page retention 分別54,800與265,744 bytes，
drop 後回 baseline。CI 對所有五 workload 強制 peak ≤768 KiB、retained ≤272 KiB，
且不忽略錯誤／取消／配置殘留。這是 peak **live requested allocations**，不包含
allocator 保留頁、stack 或其他程序，**不是 RSS、真磁碟 I/O 或 Host 完整記憶體結論**。
來源生成在記憶體、只有兩輪掃描；不能套成整個 named pipeline 及跨裝置的效能。

debug 版也通，但256MiB的兩 workload 需26.18／26.80秒，明確超過現有10秒pipeline

Host timeout 或舊 reader budget。仍須真磁碟、語義/名稱處理、雙來源版本與共享負載測量。
